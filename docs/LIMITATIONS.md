# Limitations

Honesty about what this build does and does not do is itself one of DAFTARI's design principles (see Rule #9 — a report that hides its own gaps is a report that lies). This document applies that same standard to the project itself.

## Why there is no gold price feature, anywhere

This is a deliberate product decision, not a missing feature. Earlier design drafts of this project included a daily reference price, fetched from Tanzania's Mining Commission and shown prominently on the Home screen. That design was abandoned for a concrete reason: gold is not a fungible commodity at the point a small-scale miner actually sells it. Purity, recovery rate, ore grade, and a specific buyer's trustworthiness all move the price a given lot fetches — often by a large margin — and none of that is captured by a single published reference figure. Showing one anyway would have taught users to measure a fair price against a number that systematically does not apply to their specific gold. The entire pricing surface — a "Bei" agent, a `PriceQuote` domain type, a price cache table, a pre-sale comparison against a reference or an average — was removed for this reason, and replaced with `Ledger.assessMargin`: a comparison between exactly two numbers, both entirely within the user's own control — what a batch cost to produce, and what a specific buyer is offering for it right now.

## Flutter toolchain verification

This codebase was written and reviewed in a sandboxed environment with **no access to the Flutter SDK, the Dart SDK, or pub.dev** (only npm, PyPI, crates.io, and a handful of other package registries were reachable). This materially changes how much can honestly be claimed about it:

**What was verified, and how:**
- Every relative and package-scoped `import` statement in `lib/` and `test/` was resolved by script against the actual file tree — zero broken imports.
- Every `{`/`}`, `(`/`)`, and `[`/`]` pair in every Dart file was counted and confirmed balanced.
- Every localization key referenced anywhere in `lib/features/` (as `l.someKey`) was cross-checked against every key the `L` class actually defines — zero undefined keys, zero unused keys left dangling after the pricing-feature removal.
- The core numerics were independently re-derived and validated in Python before being ported to Dart — see the extensive comments in `lib/domain/numerals.dart` for the specific worked examples from the Master Specification that an earlier version of this file actually failed.
- The `MarginAssessment`/`Ledger` arithmetic in this document and in `test/ledger_test.dart` was cross-checked against hand-computed Python arithmetic for exact rounding behavior.

**What was not verified, because the tooling to do so was not available here:**
- `flutter analyze` has never been run against this code. Static checks caught missing imports and balance errors; they cannot catch a type mismatch, a missing required named parameter, or an incorrect method signature the way the real Dart analyzer can.
- `flutter test` has never actually executed the 101 test cases in `test/`. Every test was hand-traced against the exact behavior of the function it tests (and several genuine bugs were found and fixed this way — see below), but "hand-traced to be correct" and "executed and passed" are not the same claim, and this README does not pretend otherwise.
- `dart run build_runner build` has never been run, so `lib/data/database.g.dart` (Drift's generated code) does not exist in this repository. The Drift schema in `lib/data/database.dart` is written correctly against Drift's documented API, but has not been compiled.
- `lib/l10n/app_localizations*.dart` were hand-generated by `scripts/gen_l10n_dart.py` rather than by `flutter gen-l10n`, as a structural stand-in. It should be regenerated with the real tool and diffed against this version before shipping.

**The right next step for anyone continuing this project is exactly one command:** `flutter pub get && dart run build_runner build --delete-conflicting-outputs && flutter analyze && flutter test`, on a machine with the actual Flutter SDK installed. Given how thoroughly the logic has already been hand-verified, the most likely remaining issues are minor — an import ordering lint, a nullability annotation Dart's analyzer is stricter about than a human reader — rather than fundamental design errors, but that is a prediction, not a guarantee.

## Real bugs found and fixed during this project

Documented here because a project that hides the bugs it already found is less trustworthy than one that shows its work:

1. **`Numerals.parse` assumed the wrong word order.** The original implementation expected a multiplier-then-scale order ("tano elfu"), but every worked example in this product's own specification actually speaks the scale word first ("elfu tano", "laki tano na nusu"). The bug produced 1,005 instead of 5,000, and 150,005 instead of 550,000, for two of the specification's own five documented test cases. Rewritten and verified against all five cases plus nine additional ones.
2. **The amount-extraction regex in `Interpreter` over-captured trailing note text.** A clause like "elfu tano ya kufrisha ponchi" could have its amount capture group greedily swallow "ya kufrisha ponchi" along with the number, causing `Numerals.parse` to correctly refuse the resulting garbled string — silently downgrading a perfectly good "5,000" into an unresolved question. Fixed with a backoff loop that trims trailing words until the numeral portion parses on its own.
3. **Counterparty extraction missed direct-object constructions.** "Nimempatia Michael..." (I gave Michael...) names its counterparty with no preposition, unlike "kwa Salimu" (to Salimu). The original regex only matched the preposition case, so the specification's own worked B1 test case ("Michael and Salimu identified") would have failed to identify Michael. Fixed by adding a direct-object-verb fallback path.
4. **The original `database.dart` used a schema entirely disconnected from the domain model** — a flat `Entries` table with `RealColumn` (floating-point) money fields and a real `deleteEntry()` method, alongside separate `Capture`/`Entry` domain classes with no code ever mapping between them. This violated Rule #6 (money must be an integer) and Rule #5 (no deletion) simultaneously, and meant the app's persistence layer could never have actually worked as designed. Rewritten from scratch with `CaptureRows`/`EntryRows` tables that mirror the domain model exactly, integer money throughout, and no delete method anywhere.
5. **`price_service.dart` (since removed) expected a JSON field, `pricePerGramTzs`, that the paired Next.js API never returned** (`perGramUnits` was the actual field name). This meant a live network fetch would always have thrown. Moot now that the pricing feature has been removed entirely, but documented here since it was a real, confirmed bug in the code as originally received.

## Bugs caught by the real Flutter toolchain, once it became available

The four bugs above were found by hand-tracing, before this project had access to a real Flutter installation. The moment a collaborator ran this code through an actual `flutter pub get` / `dart run build_runner build` / `flutter run -d chrome`, four additional real compiler errors surfaced immediately — proof that hand-verification, however careful, is not a substitute for the real toolchain, exactly as this document said above before these were found:

6. **`intl` version conflict.** `pubspec.yaml` pinned `intl: ^0.19.0`, but `flutter_localizations` (from the Flutter SDK itself) hard-pins `intl` to `0.20.2` on the version of Flutter actually installed. `flutter pub get` failed version solving outright. Fixed by bumping the constraint to `^0.20.2` — the only `intl` API this project uses (`NumberFormat.decimalPattern()` in `lib/core/money.dart`) is unaffected.
7. **`lib/data/database.dart` used `Capture` and `Entry` as method return types without importing `../domain/capture.dart` or `../domain/entry.dart` directly.** The file only imported `database_mappers.dart`, which itself imports those domain types — but Dart does not transitively re-export imported symbols, so every method returning `Capture`/`Entry` failed to resolve at compile time ("Type 'Capture' not found"). Fixed by importing both domain files directly in `database.dart`.
8. **`lib/features/capture/quick_capture_screen.dart` used `DraftEntry` (defined in `domain/interpreter.dart`) and `ConfirmationArgs` (defined in `app/router.dart`) without importing either file.** Both compiled cleanly in isolation during hand-review because the *names* were correct and the *logic* was correct — only the import statements were missing, which static text review caught for every other screen but missed here. Fixed by adding both imports.
9. **`lib/features/inbox/inbox_screen.dart` imported two unrelated classes both named `Gap`** — the spacing-token class in `theme/tokens.dart` (`Gap.md`, `Gap.lg`, used throughout every screen for padding) and the gap-detection result class in `domain/gap_detector.dart`. Dart's ambiguous-import error fired on every `Gap.xx` spacing reference in the file. Fixed with `import "../../domain/gap_detector.dart" hide Gap;`, since the screen only needs `GapKind` from that file.
10. **`dart:ffi` is not available on Flutter Web at all, and the original `database.dart` imported `dart:io` and `package:drift/native.dart` (both `dart:ffi`-dependent) directly in the shared, platform-neutral database file.** This is an architectural gap, not a typo: it meant the app could never have compiled for Flutter Web, despite the Master Specification explicitly requiring a web build. `flutter run -d chrome` failed with dozens of cascading "`dart:ffi` is not available on this platform" errors. **Fixed** by splitting the connection logic into `lib/data/connection/connection_native.dart` (the original `dart:ffi`-based `NativeDatabase`, used on Android/iOS/desktop) and `lib/data/connection/connection_web.dart` (Drift's WASM-based `WasmDatabase`, used on Flutter Web), selected via Dart's conditional-import mechanism in `database.dart`. **This fix is not yet fully verified end-to-end**: Drift's web backend additionally requires two binary/script assets (`sqlite3.wasm` and `drift_worker.js`) to be present in this project's `web/` folder, which are version-specific build artifacts this repository does not ship (see the doc comment in `connection_web.dart` for why, and a link to Drift's current official web setup guide for how to obtain them). Until those two files are added, `flutter run -d chrome` will still fail — with a single, clear, intentional error message pointing at this exact cause, rather than the dozens of confusing cascading `dart:ffi` errors from before. **Android, iOS, desktop, and `flutter test` are unaffected by this gap** and should work now.

## Agent fleet coverage

All four agents in `agents/` have working code and a Dockerfile. Test coverage is uneven by design, not oversight:

- **`agents/daftari`, `agents/mkumbushi`'s gap-detection core, and `agents/mlinganishi`'s reconciliation core** are pure, deterministic Python with no external dependency, and their test suites (27 test cases total) were actually executed in this environment — all passing.
- **The Gemini-calling portions of `agents/sikio`, `agents/mkumbushi` (question phrasing), and `agents/mlinganishi` (fuzzy name matching)** were verified for correct import paths and constructor signatures against the real, installed `google-adk` package, but were not run end-to-end against a live Gemini API key, since none was available in this environment. The prompt design and JSON-extraction logic follow the same pattern validated in the deterministic agents' HTTP layers.

## What was deliberately not built, given the time available

Consistent with the Master Specification's own approach to scope ("naming a roadmap demonstrates judgement; attempting all of it in eighteen days would demonstrate the opposite"):

- **Device-to-cloud sync** (`lib/data/` has no `sync_service.dart` yet). The app is fully functional offline without it; wiring it up is the natural next integration point once `agents/daftari` and `agents/sikio` are deployed.
- **Share-code linking between two parties.** `agents/mlinganishi` is ready to reconcile two parties' entries the moment this exists, but the on-device feature to generate and redeem a share code has not been built.
- **A real audio-file playback on the Origin screen.** Voice capture uses `speech_to_text` for a live transcript; the underlying audio is not separately saved, so the Origin screen's "play recording" control has no audio behind it in this build.
- **On-device app-lock (PIN/biometric).** Deliberately deferred, matching the Master Specification's own reasoning: a lock on a phone with no account and no recovery path risks recreating the exact "lost notebook" failure this product exists to prevent.
